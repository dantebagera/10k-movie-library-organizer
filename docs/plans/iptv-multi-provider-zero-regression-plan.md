# IPTV Multi-Provider Zero-Regression Plan

- **Status:** Approved for planning; multi-provider implementation has not started.
- **Last reviewed:** 2026-07-27
- **Target:** Cinema Paradiso desktop IPTV workspace and Settings.
- **Existing provider:** The current Lionz account is configured and must survive migration.

## Objective

Allow Cinema Paradiso to configure, synchronize, browse, organize, and play media from multiple independent Xtream providers without mixing provider ownership or allowing one provider to overwrite another.

The first implementation must:

1. Preserve the current Lionz credentials, catalog, Favorites, custom lists, history, and cached details.
2. Add provider management to Settings.
3. Add an explicit active-provider selector to the IPTV workspace.
4. Keep every catalog, synchronization, list, history, image, EPG, and playback operation provider-scoped.
5. Preserve the existing CP-native IPTV presentation and the separation between IPTV media and CP's local/TMDB catalog.
6. Re-save the current Lionz credentials through the completed multi-provider API at final runtime acceptance, without printing or documenting the secret values.

## Current State And Known Risks

### Working behavior that must be preserved

- IPTV is a first-class CP workspace with Home, Live TV, Movies, Series, Favorites, and My Lists.
- Provider categories and media are synchronized from Xtream and stored locally.
- A complete sync replaces removed provider categories and introduces new categories.
- A stale catalog can trigger a background synchronization.
- Provider media remains separate from CP's local SQL/TMDB ownership.
- Favorites and custom lists use provider snapshots so removed provider media remains understandable.
- Integrated playback uses the existing FFmpeg relay and Hls.js player.

### Current single-provider assumptions

- `data/iptv/provider.json` stores one account.
- `services/iptv_service.py` owns one config, one store, one sync state, and one playback session collection.
- `services/iptv_store.py` uses `kind + item_id` and `kind + category_id` as catalog identities.
- `replace_catalog()` deletes the complete catalog before inserting the active provider response.
- Details and watch history also use `kind + item_id` without a provider identity.
- Favorites and custom-list ownership have a `provider_key`, but their item joins still resolve against the one global catalog.
- HTTP routes and frontend API calls do not carry a provider ID.
- Settings contains one credential form and explicitly describes one active provider.
- The IPTV workspace has no provider selector.

Adding a second form without correcting these owners would overwrite Lionz and could attach list entries, details, history, artwork, or playback to another provider that happens to reuse the same Xtream ID.

## Non-Negotiable Product Contract

### Provider ownership

- Every provider has one stable opaque `provider_id` generated by CP.
- `provider_id` does not change when the provider URL, username, password, or display name changes.
- Exact duplicate accounts, defined as the same normalized server URL and username, are rejected.
- Two accounts on the same server with different usernames are allowed.
- Provider secrets are never returned by an API, written to logs, included in documentation, committed, or used in automated test fixtures.
- Password fields remain blank after loading Settings. A blank password during edit means keep the saved password.
- Every catalog, detail, EPG, image, list, history, sync, and playback request identifies its provider explicitly.
- A remembered UI selection is a preference only. The backend must never route data based on a process-global active provider.

### Catalog and user state

- Each provider has an isolated catalog and synchronization generation.
- Synchronizing provider A cannot delete, rewrite, block, or increment provider B.
- Identical category, stream, movie, series, and episode IDs may exist in different providers.
- Favorites, custom lists, list snapshots, watch history, details, and image caches remain provider-specific.
- Custom lists do not combine providers in this release.
- There is no All Providers catalog/search mode in this release.
- Removing a provider requires a precise confirmation and removes only that provider's credentials, catalog, caches, history, Favorites, custom lists, and playback sessions.
- Removing one provider cannot change another provider or CP's local movie catalog.

### IPTV workspace

- One provider is visibly active at all times when at least one provider exists.
- The IPTV header contains the provider selector, connection state, last sync time, and manual sync action.
- Cards do not repeat provider badges because the page header establishes scope.
- Switching provider:
  - stops active playback for the previous provider;
  - clears category, query, pagination, selected media, detail, EPG, and player state;
  - preserves the current Home/Live/Movies/Series/Favorites/My Lists tab where practical;
  - loads the selected provider's saved catalog immediately;
  - starts a stale-catalog sync only for that provider;
  - remembers the selection without making it an implicit backend routing source.
- A provider with no completed sync shows an honest empty/syncing state rather than another provider's catalog.

### Settings

- Replace the single IPTV credential card with one desktop provider-management surface.
- Use a provider rail and one editor; do not create nested cards or one full settings card per provider.
- The provider rail shows display name, state, last sync, and compact counts.
- The editor supports add, rename, credential update, TLS setting, test, sync, and remove.
- `Save & Test` is the primary add/update action.
- A newly added provider starts its first sync only after authentication succeeds.
- Settings summarizes the number of configured providers.

### Runtime and migration safety

- Automated tests use disposable IPTV roots and fake Xtream clients. They never use live Lionz credentials or catalog files.
- The live migration runs only after isolated migration tests pass.
- The current Lionz source files are backed up before migration and validated before the new manager becomes authoritative.
- The migration is idempotent: restarting after success does not create another Lionz provider.
- A failed migration rolls back to the pre-migration layout.
- Legacy paths are not retained as a second active implementation.
- Playback directories are ephemeral and are not migrated.

## Target Ownership

| Responsibility | Authoritative owner |
| --- | --- |
| Provider registry, stable IDs, ordering, and redacted summaries | New `IPTVProviderManager` |
| One provider's credentials, catalog, sync, images, history, lists, and playback | Existing `IPTVService`, refactored to accept an explicit provider root and ID |
| Catalog SQL behavior inside one provider | Existing `IPTVStore` |
| Xtream protocol and URL formation | Existing `XtreamClient` |
| Provider-scoped HTTP contract | Existing IPTV route module calling `IPTVProviderManager` |
| Frontend provider API contract | `src/api/iptv.js` |
| Provider management UI | Existing Settings workspace |
| Active provider and provider-scoped IPTV view state | Existing IPTV workspace |
| Playback behavior | Existing IPTV player and provider-scoped playback service |
| Legacy Lionz migration | `IPTVProviderManager` startup migration, covered by isolated tests |

Do not create separate service, store, player, or route implementations for Lionz or for the second provider.

## Target Data Layout

```text
data/iptv/
  providers.json
  migration-backups/
    <timestamp>/
      provider.json
      iptv.sqlite
      images/
  providers/
    <stable-provider-id>/
      provider.json
      iptv.sqlite
      images/
      playback/
```

`providers.json` contains only non-secret registry metadata and preference state:

```json
{
  "schema_version": 1,
  "last_selected_provider_id": "opaque-provider-id",
  "providers": [
    {
      "provider_id": "opaque-provider-id",
      "name": "Lionz",
      "position": 0,
      "created_at": 0,
      "updated_at": 0
    }
  ]
}
```

Each provider's `provider.json` remains backend-only and stores that provider's normalized server URL, username, password, and TLS choice. Registry writes and credential writes must be atomic.

## Target API

### Provider registry and credentials

```text
GET    /api/iptv/providers
POST   /api/iptv/providers
GET    /api/iptv/providers/<provider_id>
PATCH  /api/iptv/providers/<provider_id>
DELETE /api/iptv/providers/<provider_id>
POST   /api/iptv/providers/<provider_id>/test
POST   /api/iptv/providers/<provider_id>/sync
GET    /api/iptv/providers/<provider_id>/status
POST   /api/iptv/providers/selection
```

- Provider collection/detail responses are redacted.
- Add/update validates the normalized server and username before write.
- Delete closes provider playback and sync resources before removing only that provider directory.
- Selection persistence never replaces explicit provider IDs on data requests.

### Provider-scoped catalog and playback

```text
GET    /api/iptv/providers/<provider_id>/categories
GET    /api/iptv/providers/<provider_id>/items
GET    /api/iptv/providers/<provider_id>/items/<kind>/<item_id>
GET    /api/iptv/providers/<provider_id>/epg/<stream_id>
GET    /api/iptv/providers/<provider_id>/favorites
POST   /api/iptv/providers/<provider_id>/favorites/<kind>/<item_id>
GET    /api/iptv/providers/<provider_id>/lists
POST   /api/iptv/providers/<provider_id>/lists
PATCH  /api/iptv/providers/<provider_id>/lists/<list_id>
DELETE /api/iptv/providers/<provider_id>/lists/<list_id>
GET    /api/iptv/providers/<provider_id>/lists/<list_id>/items
POST   /api/iptv/providers/<provider_id>/lists/<list_id>/items/<kind>/<item_id>
PATCH  /api/iptv/providers/<provider_id>/lists/<list_id>/items/<kind>/<item_id>

GET    /api/iptv/providers/<provider_id>/recent
GET    /api/iptv/providers/<provider_id>/image/<kind>/<item_id>
```

The old singular routes are internal CP routes, not a public compatibility promise. Migrate every frontend caller and test in the same change, then remove the singular route implementation instead of preserving parallel behavior.

## Implementation Stages

### Stage 0 - Baseline, protected data inventory, and fixtures

1. Inspect the dirty worktree and preserve all existing user changes.
2. Record the exact pre-migration Lionz runtime state without exposing secrets:
   - credential flags and redacted username hint;
   - catalog generation and counts;
   - category counts;
   - Favorites/custom-list counts and list entry counts;
   - recent-history count;
   - database and image-directory sizes.
3. Confirm there are no active playback sessions before live migration.
4. Add fake provider fixtures with overlapping category IDs, stream IDs, movie IDs, and series IDs.
5. Add a disposable legacy single-provider fixture containing credentials, catalog, history, Favorites, and a custom list.

**Exit gate:** the baseline is recorded, test fixtures contain no live credentials, and no live file has changed.

### Stage 1 - Provider-root service and registry manager

1. Refactor `IPTVService` so it receives an explicit provider root and stable provider ID.
2. Keep one `IPTVStore`, credential file, image cache, playback root, sync state, and session collection per service instance.
3. Add `IPTVProviderManager` to:
   - load and atomically save registry metadata;
   - validate provider IDs and directories;
   - create, edit, rename, list, and remove providers;
   - return redacted summaries;
   - reject exact duplicate accounts;
   - construct and cache one service instance per provider;
   - close all services during app-data-root changes and shutdown.
4. Store provider display names in the registry, not in the credential file.
5. Keep provider IDs independent of credential identity.

**Automated coverage:** registry defaults, atomic save, corruption handling, ID/path validation, duplicate-account rules, same-server/different-user support, blank-password preservation, redaction, service reuse, service close, and provider-isolated roots.

### Stage 2 - Idempotent legacy Lionz migration

1. Detect the legacy layout only when `providers.json` does not exist and the old `provider.json` or `iptv.sqlite` exists.
2. Generate one stable provider ID and registry entry named `Lionz`.
3. Create a timestamped migration backup.
4. Copy the legacy credential file, SQLite database, and image cache into the new provider directory.
5. Do not migrate playback directories.
6. Open the copied database and compare protected baseline facts before activating the registry.
7. Atomically write the registry only after validation passes.
8. Move old active files out of the legacy path after activation so there is one authoritative runtime.
9. Roll back filesystem changes if any stage fails.
10. Make a second startup a no-op.

Because the existing provider-specific Favorites/custom lists use a hash of server URL and username, preserving the same credential values preserves their ownership key without rewriting list rows.

**Automated coverage:** empty install, config-only legacy install, full legacy install, list/history preservation, cached-detail preservation, missing images, interrupted migration rollback, idempotent second startup, and no active legacy path after success.

### Stage 3 - Provider-scoped backend routes

1. Replace the singular route contract with the provider registry and provider-scoped routes.
2. Resolve provider ID once at the route boundary and call that service.
3. Reject unknown provider IDs with a clear 404.
4. Keep secret fields out of all errors and responses.
5. Build local playback relay URLs with the provider ID.
6. Keep provider TLS configuration in each playback session so switching/editing another provider cannot affect an existing stream.
7. Update app-data-root switching to construct and close the manager rather than one service.
8. Remove obsolete singular config/status/sync/data routes after all internal callers migrate.

**Automated coverage:** route redaction, provider CRUD, unknown IDs, same media IDs across providers, sync isolation, detail/EPG/image isolation, history/list isolation, playback URL ownership, TLS-session isolation, provider deletion isolation, and app-data-root manager replacement.

### Stage 4 - Frontend API and Settings provider manager

1. Replace ambient IPTV API methods with methods requiring `providerId`.
2. Add provider registry CRUD/test/sync methods.
3. Replace the single Settings IPTV form with:
   - provider rail;
   - add-provider action;
   - one selected-provider editor;
   - display name, server URL, username, password, and TLS fields;
   - redacted saved-account hint;
   - Save & Test, Sync, and Remove actions;
   - per-provider status, expiry, last sync, and counts.
4. A new provider is saved and authenticated before its first sync begins.
5. Failed authentication leaves an editable provider but does not start sync or expose credentials.
6. Removal requires the provider name in a confirmation and clearly states which provider-specific data will be removed.
7. Keep this desktop-only; do not redesign unrelated Settings sections.

**Automated coverage:** add/edit/rename, blank-password preservation, test success/failure, first-sync gate, duplicate provider error, rail selection, counts/status, removal confirmation, selection after removal, and unchanged non-IPTV Settings behavior.

### Stage 5 - IPTV provider selector and state isolation

1. Add the active-provider selector to the existing IPTV header beside sync status/action.
2. Show display name, connection state, last sync, and compact counts in the selector menu.
3. Add Manage providers, which opens Settings at the IPTV provider section.
4. On provider switch:
   - stop the previous playback token;
   - reset provider-specific React state;
   - request the selected provider status, recent history, categories, lists, and catalog;
   - preserve the current media tab where valid;
   - persist the selection preference;
   - run the stale-catalog policy for the selected provider only.
5. Key category, catalog, details, EPG, recent, list, and playback state by provider or clear them synchronously before the next provider renders.
6. Ensure late responses from the previous provider cannot update the newly selected view.
7. Do not add provider badges to cards or an All Providers mode.

**Automated coverage:** empty-provider state, one-provider state, switching, stale-response cancellation, same item IDs, state reset, playback stop, tab preservation, selection persistence, stale sync per provider, and Settings navigation.

### Stage 6 - Full verification and live Lionz acceptance

1. Run focused manager, service, store, route, migration, UI, and policy tests.
2. Run the complete isolated Python suite with a disposable `CP_TEST_ROOT`.
3. Run frontend Node tests.
4. Run `npm.cmd run build`.
5. Run desktop Playwright against a disposable server and provider fixtures.
6. Verify two fake providers can:
   - hold identical IDs without collision;
   - sync independently;
   - maintain separate Favorites, custom lists, history, details, and images;
   - switch without stale UI;
   - start and stop separate playback sessions.
7. Only after all isolated checks pass, migrate the live legacy Lionz data.
8. Compare the post-migration Lionz database facts with the Stage 0 baseline before any fresh provider sync.
9. Re-save the Lionz provider through the new provider update API using the values read locally from the migrated credential file:
   - do not print, log, paste into documentation, or return the password;
   - preserve the existing TLS choice;
   - verify the response contains only redacted flags/hints;
   - call Test and require successful Xtream authentication;
   - confirm the credential file is saved under the Lionz provider directory.
10. Open CP Settings and confirm Lionz appears in the provider rail.
11. Open IPTV and confirm Lionz is selected, its saved catalog is available, and its custom list and Favorites remain.
12. Add a disposable second test provider through the real UI or a controlled local fixture, prove switching, then remove only the disposable provider.
13. Do not delete the migration backup until Dante accepts the result.

## Regression Requirements

- Existing Lionz catalog counts and user state survive migration before any fresh sync.
- No secret appears in Git diff, test output, logs, browser snapshots, documentation, or API payloads.
- Existing app-data-root switching still closes IPTV processes and reopens the correct root.
- Existing single-provider users are migrated automatically and see Lionz selected.
- New installs with no provider show a provider setup state.
- Syncing one provider never changes another provider's generation or counts.
- Removing one provider never changes another provider or local CP catalog.
- Same provider IDs across accounts never cross-link details, artwork, Favorites, lists, history, or playback.
- Automatic sync does not duplicate a running provider sync.
- Provider category refresh still introduces new categories and removes deleted categories.
- Live playback, VOD playback, cleanup, and bounded recovery retain their existing behavior.
- Existing Home, Library, Movie Lists, Maintenance, Discover, AI Control, Downloads, Help, Settings, and shared cards remain green.

## Explicit Non-Goals

- Combining provider catalogs into one search or All Providers view.
- De-duplicating equivalent movies, channels, or series across providers.
- Sharing Favorites or custom lists across providers.
- Importing M3U providers or non-Xtream protocols.
- Provider logos, commercial branding, or custom card designs.
- Mobile or responsive redesign.
- Replacing the FFmpeg/Hls.js playback architecture.
- Solving the separately identified live-browser stall within this migration unless a provider-scoping change directly requires it.
- Changing CP's local movie SQL catalog, TMDB identity, ownership, downloads, or qBittorrent behavior.

## Stop Conditions

Stop implementation and report evidence before touching live data if:

- isolated legacy migration loses a list, Favorite, history row, detail row, or catalog item;
- a credential can appear in an API response or log;
- the manager requires a process-global active provider for routing;
- provider deletion can escape its own root;
- same-ID fixtures cross providers;
- the current dirty worktree creates an irresolvable ownership conflict;
- live Lionz files differ unexpectedly from the recorded baseline before migration.
